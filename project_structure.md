# Структура проекта vintage-estimator

Этот файл объясняет, как мы раскладываем проект по схеме модулей (`imgs/img.png`).

## Где лежит код

Работаем в своём собственном репозитории (этом), не в форке общего курсового репозитория — преподаватель позже сам сольёт нужное к себе. Поэтому вся структура лежит прямо в корне:

```
vintage-estimator/
├── README.md
├── pyproject.toml
├── uv.lock
├── src/
│   └── vintage_estimator/
├── tests/
├── examples/
└── docs/
```

## Принцип раскладки

Репозиторий читается не как список файлов, а по пяти вопросам:

1. **Как запускается?** — `README.md`, `pyproject.toml [project.scripts]`
2. **Из чего состоит?** — `src/`
3. **От чего зависит?** — `pyproject.toml`, `uv.lock`
4. **Как проверяется?** — `tests/`
5. **Где путь поведения?** — entry point → сервис → модуль → тест

Используем **src-layout**: весь импортируемый код лежит в `src/vintage_estimator/`, а не в корне проекта и не в папке `src` как "имени пакета" (`import vintage_estimator`, а не `import src.vintage_estimator`).

## Разбивка на модули (по схеме img.png)

Каждый блок схемы — это подпакет внутри `src/vintage_estimator/`, а не отдельный репозиторий. Это даёт один `pyproject.toml`, один набор зависимостей и возможность запускать всё как единое приложение, при этом каждый участник отвечает за свою папку.

```
src/vintage_estimator/
├── __init__.py
├── __main__.py              # python -m vintage_estimator
├── preprocessing/           # Зеленин Денис
│   └── __init__.py
├── encoder/                 # Зеленин Денис
│   └── __init__.py
├── classifier/               # Зеленин Денис
│   └── __init__.py
├── retriever/                # Кустарев Александр
│   └── __init__.py
├── price_prediction/         # Кустарев Александр
│   └── __init__.py
└── api/                       # Кустарев Александр
    └── __init__.py
```

Зона ответственности (как в README.md):
- **Препроцессинг → Энкодер → Классификатор** — Зеленин Денис
- **Ретривер → Предсказание цены → API** — Кустарев Александр

## Контракты между модулями

По схеме между блоками идут конкретные структуры данных — это и есть границы ответственности, которые нужно зафиксировать до начала параллельной разработки:

| Откуда → куда | Что передаётся |
|---|---|
| Препроцессинг → Энкодер | обработанная картинка |
| Энкодер → Ретривер | эмбединг |
| Энкодер → Классификатор | эмбединг |
| Ретривер → БД | запрос эмбединга |
| Ретривер → Предсказание цены | топ-k похожих предметов |
| Классификатор → Предсказание цены | категория |
| Классификатор/Предсказание цены → API | результат (предмет, стиль, цена, похожие предметы) |

Пока второй модуль не готов, его можно подменить заглушкой с этим же контрактом (например, функция `encode(image) -> np.ndarray` возвращает случайный вектор фиксированной размерности) — это позволяет обеим сторонам разрабатывать и тестировать независимо.

`tests/` зеркалит структуру `src/`, чтобы было видно, какое поведение каждого модуля зафиксировано.

## pyproject.toml — паспорт проекта

Один файл на всю команду:

- `[project]` — имя, версия, `requires-python`, общие runtime-зависимости (torch, fastapi и т.п.)
- `[project.optional-dependencies]` — можно разделить тяжёлые ML-зависимости (`ml = [...]`) и API-зависимости (`api = [...]`), если кто-то хочет ставить только свою часть
- `[project.scripts]` — точка входа, например `vintage-estimator = "vintage_estimator.api.cli:main"`
- `[tool.pytest.ini_options]` — `pythonpath = ["src"]`, `testpaths = ["tests"]`
